# Approved browser files and Harness agent

Open `/harness-files`. Select a UTF-8 file (at most 128 KiB), request and approve its read. Optionally enter an instruction and review the **exact selected content and instruction** before separately approving their transmission. The server runs a real Harness agent whose only custom tool, `read_selected_content`, returns that single in-memory snapshot once; it has no path parameter, filesystem store, shell, web access or file-writing tool. The model may choose not to call the tool. The selected content and instruction go only to fixed local oMLX at `http://127.0.0.1:8001/v1`, using `Qwen3.8-27B-oQ4e-mtp`; there is no external or catalogue fallback. This model and endpoint must be available and support tool calling. The local model service and other local processes remain part of the trust boundary and may have their own logging or retention; do not use secrets.

The suggestion is untrusted and may be incorrect or follow instructions embedded in the file. Review it, optionally append it to or replace the editor content, then request and separately approve the **exact displayed filename and download contents**. The browser chooses where to save. The application never writes the source or a server filesystem file. Changing the editor or instruction after a review does not change the approved snapshot; selecting a new file cancels an in-flight request and clears its approval. Denial discards the pending operation. No content is intentionally stored in browser storage or server session state; data exists in browser, request, agent and model-service memory while in use. There is no durable session or resume, and navigating away aborts the browser request; a model server may not immediately stop work on cancellation.

Requests and output are bounded (128 KiB each; instruction 4,000 characters), the server permits two concurrent runs and times out after two minutes. Request transport is same-origin through a proxy that accepts loopback peers only, requiring the configured `Delegation:AllowedOrigin` to match the browser origin exactly. The endpoint is for a trusted local installation, not authentication against other local processes. No OS sandbox is claimed. Harness telemetry and HTTP body logging are disabled for this endpoint, but independent infrastructure and the model service are outside that guarantee.

Validate with `node --test tests/file-workflow/*.test.mjs` and the server test project. Browser tests stub the endpoint; server tests use a scripted model to verify actual Harness tool execution. Neither proves a real model will call the tool or produce useful results.

An opt-in live integration check is available with `RUN_LOCAL_FILE_MODEL_TEST=1 dotnet test --project tests/AGUIWebChat.Server.Tests`; it sends synthetic text to the fixed local model and checks that Harness invokes the read tool. Normal tests use a scripted model and browser endpoint stub.
